## 1. 这个项目到底是什么

### 1.1 一句话

给烹饪实训室装一套「**在工位上看、按环节评**」的系统：摄像头采集操作过程，系统按环节识别并计时，课堂结束时学生的实训成绩已经生成，教师只需要复核与归档。

### 1.2 它解决的真实问题

一堂烹饪实训课 30–40 人，教师不可能同时盯住每个工位的操作细节。结果是：

| 现状 | 后果 |
| --- | --- |
| 靠教师巡场、凭印象打分 | 同一份作品，不同教师给分不一致 |
| 只看成品，不看过程 | 刀工、火候、步骤顺序这类过程性问题无法追溯 |
| 纸质记录、课后补录 | 数据滞后，学生拿不到可改进的反馈 |
| 无法复盘 | 学生问「我哪里丢的分」，教师说不出具体环节 |

系统的做法是把**过程**变成数据：七个环节各留一份记录，最后按权重合成总分，每一分都能点开看来源。

### 1.3 七个模块与三个角色

七个模块对应一节课的时间顺序，顺序不能乱：

| 序号 | 模块 | 路由 | 一句话 |
| --- | --- | --- | --- |
| 01 | 人脸识别签到 | `/face-checkin` | 进入工位即签到，身份与本次任务绑定 |
| 02 | 着装规范识别 | `/modules/uniform` | 厨师服 / 帽 / 围裙 / 头发 / 饰物逐项判定 |
| 03 | 食材预处理评价 | `/modules/ingredient` | 切配动作识别，统计切丝频率与均匀度 |
| 04 | 烹饪过程评价 | `/modules/cooking` | 六个步骤自动分段计时，跳步与超时提示 |
| 05 | 菜肴成品分析 | `/modules/dish` | 拍照上传，五维评分 + 文字评语 |
| 06 | AI 综合评价 | `/modules/summary` | 按权重合成总分，生成个人实训报告 |
| 07 | 智能 AI 老师 | `/chat` | 发成品图或菜谱 PDF，讲难点、讲练法 |

三个角色不是「功能开关」，是三条工作流：

| 角色 | 关心什么 | 能看到什么 | 不能做什么 |
| --- | --- | --- | --- |
| 学生 | 我这节课做得怎么样 | 自己的五环节得分、待办、自己的问答记录 | 看不到班级排名与同学成绩 |
| 教师 | 这一分是怎么来的 | 班级名单、全员录像、模块判定结果 | 不改模型分数，只追加人工扣分 |
| 管理员 | 谁在用、系统稳不稳 | 全站态势、账号体系、通知 | 不参与任何评分 |

### 1.4 技术栈与分工

| 层 | 技术 | 谁负责 |
| --- | --- | --- |
| 前端 | Vue 3 + TypeScript + Element Plus + Pinia + Vue Router + Vite | 本项目已完成 |
| 后端 | FastAPI + MySQL（+ Redis、WebSocket） | 与教师共同开发 |
| AI 推理 | PyTorch / ONNX 目标检测、多模态大模型 API、LangChain + 向量库 | 后端侧 |

**当前状态**：前端全部页面与交互已完成，接口按契约预留，`VITE_USE_MOCK=true` 时用本地模拟数据跑通全流程；后端按接口表实现后，改一个环境变量即可切换。

## 2. 五分钟跑起来

### 2.1 直接运行（已有 Node）

```bash
cd frontend
npm install          # 第一次要装依赖，约 1–3 分钟
npm run dev          # 启动开发服务器
```

浏览器打开 <http://localhost:5173>。

### 2.2 演示账号

Mock 模式下密码统一是 `123456`，登录页有三个一键填充按钮：

| 账号 | 角色 | 你会看到 |
| --- | --- | --- |
| `admin` | 系统管理员 | 全部菜单、通知发布、用户管理；没有浮空球 |
| `teacher_chen` | 任课教师 | 班级态势、在评学生切换、复核扣分 |
| `2023010101` | 学生（陈子豪） | 只有自己的成绩、智能 AI 老师 |

### 2.3 推荐的第一条动线（约 3 分钟）

1. 打开 `/` 官网 → 看首屏与「三个角色」分区；
2. 用 `teacher_chen` 登录 → 工作台 → 着装规范识别，左上角切换学生，点「重新判定该生画面」；
3. 同一页面下拉到底 → 教师复核，勾选违规项 → 记一次扣分；
4. 换 `2023010101` 登录 → 智能 AI 老师，发一张成品图；
5. 换 `admin` → 用户管理点姓名看学生档案 → 补录人脸照片。

### 2.4 检查构建是否健康

```bash
npm run type-check   # 类型检查，必须 0 错误
npm run build        # 生产构建，必须成功
npm run preview      # 预览构建产物（4173 端口）
```

两个命令都过，才算「没把项目改坏」。**只跑 type-check 不够**——SCSS 变量写错只有 build 阶段才会报。

### 4.4 全局约定（改代码前必读）

1. **样式令牌唯一来源**：`variables.scss`。页面里出现 `#2f54eb`、`32px` 这类硬编码就是错的。
2. **五条视觉纪律**写在 `variables.scss` 头部：单一强调色、真中性灰、禁止装饰性彩条、三档阴影、动效统一取值。
3. **新增模块分层顺序**：`types/` → `api/` → `stores/` → `views/` → `router/`。不要为了快，把请求直接写在页面里。
4. **统一响应格式** `{ code, data, message }`，`utils/request.ts` 自动拆包，业务层只拿 `data`。
5. **流式请求不用 EventSource**：`utils/sse.ts` 用 `fetch + ReadableStream`，因为要带 `Authorization` 头。
6. **改完必须双通过**：`npm run type-check` + `npm run build`。

### 4.5 文件与素材规矩

**先分清三类文件，别一视同仁地"清理"：**

| 类别 | 有哪些 | 规矩 |
| --- | --- | --- |
| 要改的 | `frontend/src/**`、`README.md`、`docs/项目完整指南.md` | 改完双通过 + 首页截图复核 |
| 只读的 | `.codex/skills/`（57MB 六个 Skill 镜像）、`design-system/`（MASTER.md + tokens）、`docs/reference/`（立项材料） | 整目录替换式更新，不逐文件手改 |
| 可再生的 | `frontend/dist/`、`node_modules/` | 已在 `.gitignore` 里，可随时删，`npm run build` 会重建 |

**新增照片：** 放 `assets/images/` 根层，命名用「场景-动作」小写短横线（`wok-frying.jpg`），长边 1536、质量 80 左右（单张 150–230KB）。若带 AI 生成水印，裁掉右下角那一条再入库。加进 `SiteHero` 的 `photos` 数组时，位置按一节课的时间顺序插，不要按好看程度排——那排顺序本身在讲七个模块。

**判断一个文件该不该删：** ① 全仓库搜不到 import（`grep -r "文件名" src` 为空）；② 0 字节，或只有空目录；③ 描述的是**计划**而非实现（比如早期那份写着 `docker-compose.yml`、`layout/` 的目录说明）——这类内容比没有更误导。命中任一条就删，删前确认 `git status` 里它是不是别人的活。

**一个具体教训**：`composables/useAuth.ts` 曾经和 `useRole.ts` 并存，两者都有 `can()` 但签名不同（一个收角色数组、一个收能力点）。没人 import 它，可一旦有人顺手用了，权限判断就会走到另一套逻辑上。**删除重复的权限入口比留着一个"可能有用"的文件重要。**

## 5. 三个角色的权限设计

### 5.1 唯一事实来源

`src/config/permissions.ts` 里只有三样东西：

```ts
type Capability = 'dashboard.site' | 'eval.overview' | 'module.review'
  | 'summary.class' | 'course.upload' | 'user.manage' | 'notice.publish' | 'assistant.use'

const CAPABILITIES: Record<Capability, UserRole[]> = {
  'dashboard.site': ['teacher', 'admin'],
  'module.review':  ['teacher', 'admin'],
  'user.manage':    ['admin'],
  'assistant.use':  ['teacher', 'student'],
  // ...
}
```

侧栏、路由守卫、页面内按钮**三处都读这里**，不允许在页面里写 `if (role === 'teacher')` 这种判断散落各处。

### 5.2 三层拦截

| 层 | 文件 | 作用 | 表现 |
| --- | --- | --- | --- |
| 菜单 | `router/menu.ts` | 按 `roles` 过滤；父级子项全空时整组隐藏 | 学生侧栏里没有「系统管理」 |
| 路由 | `router/index.ts` 的 `meta.roles` + `router/guard.ts` | 手输地址越权时拦回 | 学生输 `/system/user` → 弹回 `/dashboard` |
| 页面 | `composables/useRole.ts` 的 `can()` | 控制按钮/区块是否渲染 | 学生看不到「教师复核」块 |

### 5.3 同一路由，三套内容

工作台 `/dashboard` 是一个路由三个视图：

| 角色 | 数据来源 | 内容 |
| --- | --- | --- |
| 学生 | `GET /v1/dashboard/me` | 我的本节课、五环节得分、待办、只有自己的动态 |
| 教师 | `GET /v1/dashboard/overview` | 班级统计、模块对接进度、签到率、班级动态 |
| 管理员 | 同上 + `GET /v1/users` 现算 | 再叠加账号构成、未录入人脸、停用账号 |

**为什么这么设计**：一个路由三套内容比分三个路由好维护——导航结构不变，用户换角色时心智模型一致。

### 5.4 浮空助手的边界（重要）

`components/AssistantBall.vue` + `utils/assistant.ts` 只做四件事：**找功能、解释规则、排查故障、汇总数据**。

- 管理员不渲染这个组件（`assistant.use` 不含 admin）；
- 学生和学生的问题库不同（`matchIntent(input, role)`）；
- 问「这道菜多少分」「我着装合格吗」这类**识别结果**问题，一律拒答并转到模块页。

这个边界不要放宽。一旦它开始报分数，就和七个模块的功能重复，而且会出现「助手说 90、模块显示 88」这种致命矛盾。

## 6. 七个模块的实现说明

每个模块的页面结构一致：**页头（标题 + 状态徽标 + 操作按钮）→ 在评学生选择器（教师/管理员）→ 左侧演示区 → 右侧后端接入面板**。

### 6.0 教师视角：先选人，再看画面

这是最容易做错的一处。最初四个模块页都是「打开自己的摄像头」，教师登录后看到的是自己对着镜头站着——既没法评学生，也暴露了对项目的理解偏差。现在的规则是：

| | 学生登录 | 教师 / 管理员登录 |
| --- | --- | --- |
| 页面顶部 | 没有选人器 | **`StudentPicker` 在最上方**，先于所有其它控件 |
| 画面区 | `getUserMedia` 开自己的摄像头 | `ReviewStage`：该生工位的录像替代画面（播放/暂停、进度、四个时间标记） |
| 判定结果记在谁名下 | 自己 | `activeStudentId` 指向的那名学生 |
| 成品分析上传 | 可以 | **入口上锁**（不能替学生交作品），底部注明当前在评学生 |
| 综合评价 | 只看自己那一份 | 整张班级名单（**不加选人器**，页面本身就是名单） |

两个组件都在 `components/`：

- `StudentPicker.vue`：可筛选下拉（人脸缩略图 + 姓名 + 学号后四位 + 未签到标记）、上/下一个、`班级 · 工位 N`、`已签到 x / y`，右侧一句「切人后，画面与判定结果一起切换」。
- `ReviewStage.vue`：把该生的人脸照片放大 120% 后 `blur(26px)` 当磨砂底，上面压头像、姓名、`工位 · 正前方`、进度条与时间标记。`compact` 属性用于烹饪页的 4 格视频墙。

**为什么选人器在 `ModuleShell` 里而不是每个页面各写一个**：一节课是跟着人走的。选中的学生存在 `stores/review.ts` 的 `activeStudentId`，从着装切到食材、再切到成品，不用重选；如果每个页面各存一份，教师切三次模块就要选三次人，实际用起来会漏评。

页面里判断「现在是不是在评别人」只用一行：

```ts
const isReviewing = computed(() => can('module.review'))   // 学生为 false
const target = computed(() => reviewStore.activeStudent)   // 在评学生
```

切人时各页面必须 `watch(() => target.value.id, ...)` 清空上一名学生的采样数据——否则会把 A 的切丝频率记到 B 名下。

### 6.1 人脸识别签到 `/face-checkin`

- **前端**：`getUserMedia` 取流 → Canvas 画虚线引导框 + 扫描线 → 每 1.5 秒 `toBlob('image/jpeg', 0.85)` 截帧 → `FormData` POST。
- **后端**：`POST /api/face/checkin`，返回 `{ success, user, similarity, timestamp }`。
- **算法建议**：RetinaFace / MTCNN 检测 + ArcFace 512 维特征，与注册时的人脸底库做余弦相似度，阈值取 0.62–0.68。
- **验收标准**：正脸 1.5 米内识别率 ≥ 98%；同一人换帽/换眼镜仍能识别；拒绝时给出可读原因而不是「失败」。

### 6.2 着装规范识别 `/modules/uniform`

- **前端**：摄像头取帧，五个判定项（厨师服/帽/围裙/头发/饰物），8 秒自动复检一次，每次判定写入「最近检测」。
- **后端**：`POST /api/modules/uniform/analyze`（单帧）+ `GET /api/modules/uniform/records`（记录）。
- **算法建议**：YOLOv8 检测 `chef_hat / chef_coat / apron / bare_head / jewelry` 五类，按 IoU 与置信度出逐项结论；不要用图像分类直接给「合规」，逐项可解释才有用。
- **教师参与**：AI 判不出的（手部不洁、围裙没系紧）由教师在页面底部直接扣分并留痕。

### 6.3 食材预处理 `/modules/ingredient`

- **前端**：1.5 秒一个采样点，实时算当前频率、平均频率、累计刀数、均匀度，画 SVG 折线。
- **后端**：`POST /api/modules/ingredient/analyze`（整段视频）+ `POST /api/modules/ingredient/frame`（低延迟帧流）。
- **算法建议**：手腕关键点（MediaPipe Hands）纵向位移过零次数 = 切击次数；均匀度用频率序列的变异系数 `CV = σ/μ` 反推。
- **验收标准**：2mm 见方的丝，频率 1.8–2.6 次/秒为正常区间；均匀度 ≥ 80 视为合格。

### 6.4 烹饪过程 `/modules/cooking`

- **前端**：四路画面墙（当前只有第 01 路有源）+ 六步横向时间轴 + 步骤判定表（正常/偏快/偏慢）。
- **后端**：`WS /ws/cooking`（逐帧推送步骤变化）+ `GET /api/modules/cooking/segments`（历史分段）。
- **算法建议**：按「动作 + 锅具状态」分段，六步为 `备菜 → 焯水 → 烧干锅 → 加油润锅 → 翻炒 → 装盘`；用状态机约束顺序，缺一步就报「跳步」。
- **判定**：与标准时长偏差超过 ±40% 记异常（`judge()` 在前端已实现同样规则）。

### 6.5 菜肴成品分析 `/modules/dish`

- **前端**：上传/拍照 → 预览 + 扫描线 → 五维加权评分 + 评语。
- **后端**：`POST /api/modules/dish/analyze`（图片）+ `GET /api/modules/dish/rubric`（评分标准）。
- **算法建议**：多模态大模型（GPT-4o / Qwen-VL 一类）按五维打分，**输出必须结构化**（JSON schema 约束），并给出每维一句理由；色彩维度可以用主色提取 + 与标准图做直方图距离作为客观辅助。
- **权重**：外观 25% / 摆盘 20% / 色彩 20% / 工艺 20% / 创意 15%（后台可配）。

### 6.6 AI 综合评价 `/modules/summary`

- **前端**：左名单（教师/管理员）或单份报告（学生）+ 右分环节得分条 + 教师裁量单列。
- **后端**：`GET /api/modules/summary/report?student_id&task_id` + `GET /api/modules/summary/class?class_id`。
- **权重**：签到与着装 15% / 食材预处理 20% / 烹饪过程 30% / 菜肴成品 30% / 课堂问答 5%。
- **两条铁律**：① 权重与及格线可配，但历史成绩保留当时的快照；② AI 分与教师扣分**分两栏显示**，否则「这一分谁给的」永远说不清。

### 6.7 智能 AI 老师 `/chat`

见 [第 10 章](#10-智能-ai-老师附件问答怎么做)。核心边界：**给方法，不给分数**。

## 7. 后端对接手册

### 7.1 三步切换

1. `frontend/.env.development` 里 `VITE_USE_MOCK=false`；
2. 后端跑在 `http://127.0.0.1:8000`（Vite 已配好代理，见 `vite.config.ts`）；
3. 刷新页面，页面右上角徽标从 `Mock` 变成 `已连接后端`。

> 接口路径注意两层：axios 的 `baseURL` 已经是 `/api`，所以代码里写 `http.get('/v1/users')`，**实际请求是 `/api/v1/users`**。模块页面板里写的是完整路径（`/api/modules/uniform/analyze`），两者是一回事。

### 7.2 统一响应格式

```json
{ "code": 0, "data": {}, "message": "ok" }
```

- `code = 0` 表示成功，前端只把 `data` 交给业务层；
- 失败用 HTTP 状态码 + `{ code, message }`，`message` 会被直接弹给用户，**要写人话**；
- `401` 前端自动清 token 并跳登录（只提示一次，避免并发刷屏）。

### 7.3 鉴权

```
Authorization: Bearer <token>
```

登录返回 `{ token, user }`，前端存 `localStorage`（key：`culinary_ai_token`）。流式接口不能用 EventSource，就是因为要带这个头。

### 7.4 七个模块接口

| 模块 | 方法 | 路径 | 请求 | 响应要点 |
| --- | --- | --- | --- | --- |
| 人脸签到 | POST | `/api/face/checkin` | `FormData{file, user_id?}` | `{success, user, similarity, timestamp}` |
| 签到记录 | GET | `/api/face/records` | `?class_id&date&page` | `{total, list[]}` |
| 着装 | POST | `/api/modules/uniform/analyze` | `FormData{file, task_id}` | `{compliant, score, items[{key,ok,confidence}]}` |
| 着装记录 | GET | `/api/modules/uniform/records` | `?class_id&date&page` | `{total, list[]}` |
| 切配 | POST | `/api/modules/ingredient/analyze` | `FormData{video, task_id, student_id}` | `{cuts, avg_frequency, uniformity, score, curve[], duration}` |
| 切配帧流 | POST | `/api/modules/ingredient/frame` | `FormData{file, window_ms}` | `{count, frequency}` |
| 烹饪实时 | WS | `/ws/cooking` | `{action:'subscribe', task_id, stations[]}` | `{event:'step_change', station, step, start_at, end_at, confidence}` |
| 烹饪分段 | GET | `/api/modules/cooking/segments` | `?task_id` | `{steps[{key,name,start_at,end_at}]}` |
| 成品 | POST | `/api/modules/dish/analyze` | `FormData{image, task_id, student_id, rubric_id}` | `{total, dimensions[], remark, image_url}` |
| 成品标准 | GET | `/api/modules/dish/rubric` | `?id` | `{name, dimensions[{key,label,weight}], pass_score}` |

| 班级名单 | GET | `/api/modules/summary/class` | `?class_id` | `{list[{student_id,name,student_no,total}]}` |

### 7.6 SSE 的四个硬要求

```
POST /api/v1/chat
Content-Type: text/event-stream
Cache-Control: no-cache
X-Accel-Buffering: no

data: {"content":"收汁"}

data: {"content":"阶段"}

data: [DONE]
```

1. 必须以 `data: [DONE]` 收尾，否则前端会一直等；
2. 关掉 Nginx 缓冲（`proxy_buffering off;`），否则「一次性吐出全部」；
3. 不要压缩（前端已删掉 `content-encoding`），gzip 会攒包；
4. 每帧给 `{"content": "..."}` 或裸文本都兼容，前端两种都能解析。

### 7.7 推荐联调顺序

1. 登录 / `profile` / 退出 —— 打通鉴权链路；
2. 用户列表与新增（最简单的 CRUD，验证统一响应）；
3. 人脸签到（`multipart`，验证文件上传）；
4. 七个模块逐个替换：先返回**固定假数据**，把前端链路跑通，再接真实模型；
5. 最后接流式问答与 WebSocket。

先假数据、后真模型，能让你在模型还没训练好时就把前端验收掉。

## 8. 数据库设计建议

以下是建议结构（MySQL 8，`utf8mb4_0900_ai_ci`），字段名与前端类型一一对应。

```sql
-- 账号
CREATE TABLE `user` (
  id            BIGINT PRIMARY KEY AUTO_INCREMENT,
  username      VARCHAR(32)  NOT NULL UNIQUE COMMENT '学号/工号',
  password_hash VARCHAR(128) NOT NULL,
  name          VARCHAR(32)  NOT NULL,
  role          ENUM('student','teacher','admin') NOT NULL,
  phone         VARCHAR(20),
  email         VARCHAR(64),
  department    VARCHAR(64)  COMMENT '班级或教研室',
  student_no    VARCHAR(32)  COMMENT '学籍号，与 username 可能不同',
  face_photo_url VARCHAR(255) COMMENT '人脸原图，对象存储 URL',
  face_feature  BLOB         COMMENT '512 维特征，float32 序列化',
  status        TINYINT      NOT NULL DEFAULT 1 COMMENT '1 启用 0 停用',
  created_at    DATETIME     NOT NULL DEFAULT CURRENT_TIMESTAMP,
  last_login_at DATETIME
) ENGINE=InnoDB;

-- 班级与选课
CREATE TABLE class (
  id BIGINT PRIMARY KEY AUTO_INCREMENT,
  name VARCHAR(64) NOT NULL,
  grade VARCHAR(16),
  teacher_id BIGINT COMMENT '班主任/任课教师'
);

CREATE TABLE class_student (
  class_id BIGINT NOT NULL,
  student_id BIGINT NOT NULL,
  PRIMARY KEY (class_id, student_id)
);

-- 课程（一次课 = 一份菜谱 + 一个班级）
CREATE TABLE course (
  id BIGINT PRIMARY KEY AUTO_INCREMENT,
  title VARCHAR(128) NOT NULL,
  week_no INT COMMENT '第几周',
  dish_name VARCHAR(64),
  class_id BIGINT NOT NULL,
  teacher_id BIGINT NOT NULL,
  pdf_url VARCHAR(255),
  recipe_json JSON COMMENT '结构化菜谱：原料/步骤/火候',
  status ENUM('draft','published') DEFAULT 'draft',
  created_at DATETIME DEFAULT CURRENT_TIMESTAMP
);

-- 菜谱 AI 解读结果（一次生成，全班共用）
CREATE TABLE course_analysis (
  id BIGINT PRIMARY KEY AUTO_INCREMENT,
  course_id BIGINT NOT NULL,
  insights_json JSON COMMENT '[{step, type: 难点/易错点, text}]',
  model VARCHAR(64),
  created_at DATETIME DEFAULT CURRENT_TIMESTAMP
);

-- 一次实训任务（一个学生一节课一条）
CREATE TABLE task (
  id BIGINT PRIMARY KEY AUTO_INCREMENT,
  course_id BIGINT NOT NULL,
  student_id BIGINT NOT NULL,
  station_no VARCHAR(16) COMMENT '工位号',
  started_at DATETIME,
  ended_at DATETIME,
  status ENUM('running','review','archived') DEFAULT 'running',
  UNIQUE KEY uk_course_student (course_id, student_id)
);

-- 各模块的判定结果（统一表，detail 存该模块的原始结构）
CREATE TABLE module_result (
  id BIGINT PRIMARY KEY AUTO_INCREMENT,
  task_id BIGINT NOT NULL,
  module ENUM('face','uniform','ingredient','cooking','dish') NOT NULL,
  score DECIMAL(5,2),
  detail JSON COMMENT '逐项结论，各模块结构不同',
  created_at DATETIME DEFAULT CURRENT_TIMESTAMP,
  KEY idx_task_module (task_id, module)
);

-- 人脸签到记录
CREATE TABLE face_record (
  id BIGINT PRIMARY KEY AUTO_INCREMENT,
  student_id BIGINT NOT NULL,
  task_id BIGINT,
  similarity DECIMAL(5,4),
  image_url VARCHAR(255),
  created_at DATETIME DEFAULT CURRENT_TIMESTAMP
);

-- 教师人工扣分（与 AI 分数并行，绝不合并写入）
CREATE TABLE deduction (
  id BIGINT PRIMARY KEY AUTO_INCREMENT,
  task_id BIGINT NOT NULL,
  student_id BIGINT NOT NULL,
  module VARCHAR(16) NOT NULL,
  item VARCHAR(64) NOT NULL,
  points DECIMAL(5,2) NOT NULL,
  reason VARCHAR(255) NOT NULL COMMENT '学生申诉时的依据，必填',
  created_by BIGINT NOT NULL,
  created_at DATETIME DEFAULT CURRENT_TIMESTAMP
);

-- 综合评价（归档时冻结当时的权重快照）
CREATE TABLE evaluation (
  id BIGINT PRIMARY KEY AUTO_INCREMENT,
  task_id BIGINT NOT NULL,
  student_id BIGINT NOT NULL,
  total DECIMAL(5,2),
  grade VARCHAR(8),
  stages_json JSON COMMENT '五环节得分 + 权重快照',
  deduction_total DECIMAL(5,2) DEFAULT 0,
  confirmed TINYINT DEFAULT 0,
  report_url VARCHAR(255),
  UNIQUE KEY uk_task (task_id)
);

-- 通知
CREATE TABLE notice (
  id BIGINT PRIMARY KEY AUTO_INCREMENT,
  title VARCHAR(128) NOT NULL,
  type ENUM('system','feature','maintenance') NOT NULL,
  body TEXT,
  audience JSON COMMENT '["student","teacher"] 或 ["all"]',
  pinned TINYINT DEFAULT 0,
  status ENUM('draft','published') DEFAULT 'draft',
  read_count INT DEFAULT 0,
  published_at DATETIME,
  created_by BIGINT
);

-- 问答
CREATE TABLE chat_session (
  id BIGINT PRIMARY KEY AUTO_INCREMENT,
  user_id BIGINT NOT NULL,
  title VARCHAR(64),
  updated_at DATETIME DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP
);

CREATE TABLE chat_message (
  id BIGINT PRIMARY KEY AUTO_INCREMENT,
  session_id BIGINT NOT NULL,
  role ENUM('user','assistant','system') NOT NULL,
  content TEXT,
  attachments JSON COMMENT '[{id, name, kind, size, url}]',
  created_at DATETIME DEFAULT CURRENT_TIMESTAMP,
  KEY idx_session (session_id, created_at)
);

-- 文件
CREATE TABLE file (
  id BIGINT PRIMARY KEY AUTO_INCREMENT,
  owner_id BIGINT,
  url VARCHAR(255) NOT NULL,
  kind ENUM('image','pdf','video','other') NOT NULL,
  size BIGINT,
  sha256 CHAR(64) COMMENT '去重，同一份菜谱不要存多份',
  created_at DATETIME DEFAULT CURRENT_TIMESTAMP
);
```

### 8.1 三条设计说明

1. **`module_result` 用统一表 + JSON**：七个模块的判定结构差异大（着装是逐项布尔、切配是曲线、烹饪是分段），拆七张表会让「查一个人的全部环节」变成七次 join。统一表 + JSON 字段更适合这个过程。
2. **`deduction` 单独一张表**：AI 分数与教师裁量必须能分开追溯。合并写入同一个 `score` 字段是最常见的错误。
3. **`evaluation.stages_json` 存权重快照**：后台改权重后，历史成绩不能跟着变，否则上学期的分这学期被改掉。

## 9. 课程与菜谱：PDF 解析链路

### 9.1 教师侧

1. 上传 PDF（≤ 20MB）→ `POST /v1/courses`（`multipart/form-data`）；
2. 后端抽取文本：优先 `pdfplumber` 取文字层；扫描件走 OCR（PaddleOCR）；
3. 让大模型把文本结构化成 `recipe_json`：

```json
{
  "dish": "糖醋里脊",
  "ingredients": [{ "name": "猪里脊", "amount": "300g" }],
  "steps": [
    { "index": 1, "action": "切条", "heat": "-", "duration": 180 },
    { "index": 2, "action": "腌制", "heat": "-", "duration": 600 }
  ]
}
```

4. 再让它输出解读：`insights: [{ step: 3, type: "难点", text: "..." }]`。

### 9.2 关键约束

- `insights[].step` 必须与 `steps[].index` **严格对齐**。落错行，学生看到的「难点」会挂到错误的步骤上——这是这条链路最容易出的 bug。
- 解读只生成一次，全班共用（`course_analysis`），不要每个学生各生成一遍，浪费 token。
- 学生端只读，教师端才有「让 AI 读一遍」的按钮。

## 10. 智能 AI 老师：附件问答怎么做

### 10.1 为什么要做成「老师」而不是「问答机器人」

学生卡住的时候，往往说不清问题：手上有一张成品图、一份老师发的菜谱。让他**把图或 PDF 直接扔进来**，比让他描述「我的汁有点稀」有效得多。

### 10.2 前端已经做了什么

| 能力 | 实现位置 | 说明 |
| --- | --- | --- |
| 选文件 | 回形针按钮 / 点入口卡 | `accept="image/*,application/pdf"`，一次最多 4 个，单个 ≤ 20MB |
| 拖拽 | `.chat-shell` 的 dragover/drop | 拖动时整块输入区高亮并显示「松手即可添加」 |
| 粘贴 | 输入框 `@paste` | 截图后 Ctrl+V 直接进来 |
| 缩略图 | `URL.createObjectURL` | 图片给缩略图，PDF 给文件卡 |
| 消息内展示 | `ChatMessage.vue` | 发出去之后仍然看得到自己发了什么 |
| 发送 | `chatStore.send(text, attachments)` | 只发附件不写字也允许 |

真实上传时：先 `POST /v1/files` 换 `file_id`，再放进 `/v1/chat` 的 `file_ids`。代码里已经预留这个字段（`stores/chat.ts`）。

### 10.3 后端提示词建议

系统提示词要写死三件事：

```
你是烹饪专业实训课的助教。
1. 学生发成品图：先指出图上能看到的事实（形态、色泽、摆盘），再给 2-3 条可执行的改法，最后给一个练习建议。
2. 学生发菜谱 PDF：先概括这道菜的流程结构，再按步骤标出难点与易错点。
3. 不评价分数、不判断合规，也不猜学生看不见的信息。学生问分数，告诉他去「AI 综合评价」看。
```

第 3 条是关键：没有这条约束，模型会热情地给出「这道菜大概 85 分」，和评价模块直接冲突。

## 11. 论文（或结题报告）撰写指南

### 11.1 先定选题表述

不好的写法：「基于 Vue 的烹饪评价系统设计与实现」——太泛，像课程作业。
好的写法：「**面向烹饪实训过程的多模态智能评价系统设计与实现**」——有场景、有技术、有对象。

关键词建议：过程性评价；计算机视觉；多模态大模型；烹饪实训；FastAPI。

### 11.2 章节结构与字数分配（以 1.5 万字为例）

| 章 | 标题 | 字数 | 必须有的东西 |
| --- | --- | --- | --- |
| 1 | 绪论 | 2000 | 背景与意义、国内外研究现状、研究内容、论文结构 |
| 2 | 需求分析 | 2200 | 三类用户、用例图、功能需求表、非功能需求（性能/安全/兼容） |
| 3 | 系统设计 | 3000 | 总体架构图、功能模块图、数据库 ER 图与表结构、接口设计 |
| 4 | 关键技术 | 2500 | 目标检测、人脸比对、多模态评分、RAG、SSE |
| 5 | 系统实现 | 3000 | 前端实现、后端实现、AI 服务、关键代码与界面截图 |
| 6 | 系统测试 | 1800 | 功能测试用例表、接口测试、性能测试、兼容性 |
| 7 | 总结与展望 | 800 | 完成的工作、不足、后续方向 |

### 11.3 每一章写什么（以及最容易写偏的地方）

**第 1 章 绪论**
- 背景要落到具体场景：「一堂 40 人的实训课，教师平均在每个工位停留不到 90 秒」比「随着我国职业教育的发展」有用一百倍。
- 研究现状分两类写：过程性评价的研究、CV/多模态在教学评价中的应用。各引 5–8 篇，其中近三年不少于一半。
- **别写**「本系统采用了先进的技术，具有广阔的应用前景」。

**第 2 章 需求分析**
- 先给三类用户的**目标**，再给功能。学生的目标是「知道自己哪里丢分」，不是「登录后能看列表」。
- 用例图至少画三个角色，学生与教师的用例要有明显差异（这是本系统的卖点）。
- 非功能需求要具体：首屏 ≤ 2s、单帧识别 ≤ 800ms、支持 4 路并发、断网可补传。

**第 3 章 系统设计**
- 架构图分三层：展示层（Vue）/ 业务层（FastAPI）/ 智能层（模型服务），加一条「视频流」的旁路。
- 数据库 ER 图至少包含 8 张核心表（见第 8 章），要标主外键与主要字段。
- 接口设计用表格：路径 / 方法 / 入参 / 出参 / 说明。**七个模块各一行**。

**第 4 章 关键技术**（这一章决定论文的技术含量）
- 每个技术点写「为什么选它 + 怎么用 + 效果如何」，不要抄原理教科书。
- 例：人脸比对为什么用 ArcFace 而不是直接比像素；切丝计数为什么用关键点位移过零而不是光流；多模态评分为什么要约束 JSON 输出。

**第 5 章 系统实现**
- 按「一屏一说」组织：每小节一个界面 + 一段说明（解决什么问题、关键交互、接口）。
- 代码只贴关键片段（≤ 30 行），前后要有解释。整页贴代码会被判为凑字数。

**第 6 章 系统测试**
- 功能测试用例表：编号 / 模块 / 前置条件 / 操作 / 预期 / 实际 / 结论。至少 20 条。
- 性能测试：单帧接口 P95 延迟、四路并发 CPU/GPU 占用、首屏加载时间。
- 兼容性：Chrome 120+ / Edge 120+，分辨率 1366×768 至 1920×1080；摄像头必须 HTTPS 或 localhost（写进论文是一个加分点）。

**第 7 章 总结**
- 老实写不足：模型只在实验室数据上验证、菜品类别有限、未做大规模压力测试。**评审最反感的是「本系统完美无缺」**。

| --- | --- | --- |
| 架构图 | 1 | 三层 + 视频旁路 |
| 用例图 | 1 | 三角色 |
| 功能模块图 | 1 | 七大模块 |

| 测试图表 | 2 | 延迟分布、识别准确率对比 |

截图要求：统一分辨率（建议 1440×900）、隐藏浏览器边框、不要出现 Mock 数据之外的无关内容、每张图都要有图题（图 5-1 …）。

## 13. 故障排查（20 条）

### 前端

1. **白屏，控制台 `ERR_ABORTED` + 500**
   SCSS 编译失败。看终端第一条报错，多半是某个 `.scss` 用了未定义的变量。`type-check` 查不出来，必须 `npm run build`。
2. **`Undefined variable` 但变量明明定义了**
   `additionalData` 只注入 `.vue` 和入口 scss；被 `@use` 的 partial 需要自己 `@use './variables.scss' as *;`。
3. **改了数据页面不更新**
   `arr.push(obj)` 之后要重新从数组取引用：`const item = arr.value[arr.value.length - 1]`，直接改 `obj` 不会触发更新（仓库里踩过两次）。
4. **子组件样式不生效**
   `scoped` 样式不会传给子组件（没有共同 `data-v`）。共用类（如 `.btn`）必须放全局样式表。
5. **媒体查询在 1440 视口下命中**
   `@media (max-width: 1440px)` 在刚好 1440 时成立。断点写 1280。
6. **摄像头黑屏**
   必须 HTTPS 或 `localhost`；局域网 IP 走 HTTP 时浏览器直接拒绝 `getUserMedia`。
7. **刷新 404**
   history 模式需要服务端兜底：Nginx `try_files $uri $uri/ /index.html;`。
8. **数字列不对齐**
   加 `font-variant-numeric: tabular-nums`（项目里 `.num` 类已封好）。
9. **字体没生效**
   不要声明未加载的 Web Font；本项目只用系统栈。
10. **首屏慢**
   图片懒加载 + `fetchpriority`；Element Plus 全量引入约 339KB gzip，可按需引入优化。

### 后端 / 联调

11. **`VITE_USE_MOCK=false` 后全是 404**
    路径少了一层 `/api`：axios 的 `baseURL` 已经是 `/api`，代码里只写 `/v1/xxx`。
12. **跨域报错**
    开发期用 Vite 代理（已配）；生产用 Nginx 同域反代，别在前端开 CORS 绕。
13. **SSE 一次性吐出全部内容**
    代理缓冲没关：Nginx 加 `proxy_buffering off;`，并确保不 gzip。
14. **SSE 请求永远不结束**
    后端没发 `data: [DONE]`。
15. **`401` 后页面死循环跳登录**
    登录接口本身也返回了 401。登录、注册、刷新 token 的请求要排除在 401 拦截之外。
16. **上传大图很慢 / 内存爆**
    前端压到 1280px 长边（`compressImage`）；后端限制 `Content-Length` 并流式落盘。
17. **图片方向不对**
    手机拍照带 EXIF 旋转；后端用 `PIL.ImageOps.exif_transpose` 纠一次。
18. **PDF 解析出来是空的**
    扫描件没有文字层，必须走 OCR。
19. **多路视频 CPU 打满**
    抽帧而不是全帧率推理：15fps 抽帧、按工位排队、GPU 批处理。
20. **人脸比对总是不通过**
    底库照片与现场光照差异过大。注册环节就要求：正脸、无遮挡、光线均匀、分辨率 ≥ 480×640。
