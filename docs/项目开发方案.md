## 1. 项目背景与目标

### 1.1 背景

烹饪工艺类实训课的考核长期依赖教师现场目视 + 事后回忆打分，存在三个结构性问题：

1. **过程不可回溯**。一节课 40 分钟、一个班 30 人，教师无法同时观察每个人的刀工、火候与卫生动作；
   期末复盘时只剩一个总分，说不清「这一分为什么扣」。
2. **口径不一致**。同一道菜、同一个班，两位教师给出的分数可能差 10 分以上，学生不服气，
   教研组也拿不出可复核的证据。
3. **过程数据被浪费**。工位摄像头录了整节课，但录完就没人再看；这些素材本可以变成教学资产。

### 1.2 建设目标

| 编号 | 目标 | 可度量指标 |
| --- | --- | --- |
| G1 | 把一节课的评价拆成五个可核对的环节 | 环节权重合计 1.0；每个环节分可下钻到原始记录 |
| G2 | 让分数可溯源 | 任一分数可点开看到「哪台设备、哪一刻、哪张抓拍」 |
| G3 | 统一评分口径 | 同一份录像，两位教师复核差异 ≤ 5 分（试点班验证） |
| G4 | 降低教师事务性负担 | 签到、着装初筛、环节计时自动化，教师只做复核与例外处理 |
| G5 | 学生可自查 | 学生能看到自己的环节分、趋势与教师评语，不必等期末 |

### 1.3 一句话定位

> **不是「AI 替老师打分」，而是「把老师本来就在看的东西，逐条留痕、可复查」。**
> 系统输出的是**建议分**，最终成绩由教师确认或修改后归档。

这条边界必须写进所有对外材料，它决定了三件事：AI 结果永远可被教师覆盖；争议时以教师的修改记录为准；
系统的免责说明（照片不能判定口味、内部熟度与食品安全）不可删除。

## 2. 建设范围与边界

### 2.1 本期做什么

| 板块 | 内容 |
| --- | --- |
| 评价主链路 | 人脸签到 → 着装规范 → 食材预处理 → 烹饪过程 → 菜肴成品 → 综合评价归档 |
| 教学支撑 | 课程与菜谱管理、菜谱难点解析、课堂问答（智能 AI 助手） |
| 学生侧 | 工作台、我的课程、我的实训档案、我的成绩、个人中心 |
| 教师侧 | 班级名单与白名单导入、选人复核、扣分与改分、成绩导出 |
| 管理侧 | 用户与角色、通知公告、工位与设备、模块交付进度 |
| 对外 | 官网与留资（`/`、`/demo`）、隐私政策与服务条款 |

### 2.2 本期不做什么（明确排除，避免验收扯皮）

| 不做 | 原因 | 替代方案 |
| --- | --- | --- |
| 自动定成绩、直接进教务系统 | 责任主体必须是教师与学校 | 导出 CSV / 打印 A4 报告，由教务处录入 |
| 真实视频流的跨网分发 | 涉及带宽与隐私，成本高于收益 | 一期用同网段拉流 + 工位录像回看 |
| 移动端 App | 学生扫码签到用 H5 已够 | 响应式 + 后续小程序（`Taro` 已验证可行） |
| 多校区 / 多租户 | 一期只有一所院校 | 数据模型预留 `school_id`，不实现隔离逻辑 |
| 情绪识别、疲劳识别等生物特征推断 | 合规风险（《个人信息保护法》敏感信息） | 只做与教学动作直接相关的判定 |
| 全自动菜谱生成 | 与评价主线无关 | 教师上传 + AI 解读难点 |

### 2.3 关键假设

- 每个工位至少 1 路摄像头，工位号与学号可绑定（`seat` 字段）。
- 学生注册时完成人脸采集，且本人同意用于签到比对。
- 教师接受「AI 建议 + 人工确认」的工作方式，不做「一键出成绩」。
- 评估网络为校内网，不考虑公网弱网下的视频回传。

## 3. 需求分析

### 3.1 角色与关注点

| 角色 | 谁 | 每天第一件事 | 决策关注点 | 不可越过的边界 |
| --- | --- | --- | --- | --- |
| 学生 | 在册学生 | 看今天上什么课、签到了没 | 我这节课得了多少、扣在哪 | 看不到别人成绩，看不到概览与系统管理 |
| 教师 | 任课教师 | 看今天这个班到齐没、有哪些待复核 | 谁需要重点讲、分数对不对 | 不能改账号与角色，不能跨班看成绩 |
| 管理员 | 信息中心 | 账号是否齐全、系统是否正常 | 交付进度、账号与设备 | 不参与评分，无 AI 助手，不替教师打分 |

> **三个角色是三条工作流，不是三个权限开关。** 同一路由按角色渲染不同内容
> （`views/dashboard/index.vue` 是范例），而不是复制三个页面。

### 3.2 核心场景（按一节课的时间轴）

| 时间 | 场景 | 系统动作 | 教师动作 | 学生动作 |
| --- | --- | --- | --- | --- |
| 课前 | 布置实训 | 教师上传菜谱 → 生成难点标注 | 上传 PDF、确认班级 | 读菜谱、看难点 |
| 08:00 | 签到 | 人脸比对（多人同框） | 处理迟到/未注册 | 刷脸签到 |
| 08:05 | 着装检查 | 帽子/上衣/围裙/袖口/发网五项判定 | 复核误判 | 按提示整理 |
| 08:15 | 备菜 | 切配频率与均匀度 | — | 正常操作 |
| 08:30 | 烹饪 | 六步时序判定 + 事件播报 | 确认事件（跳步、离岗） | 按播报纠正 |
| 09:10 | 成品 | 五维评分（色泽/摆盘/刀工/火候/卫生） | 改分 + 写原因 | 上传成品照 |

| 课后 | 复盘 | 档案趋势、课程问答 | 导出成绩单 | 问 AI 助手 |

## 4. 总体架构

### 4.1 分层

```
┌──────────────────────────────────────────────────────────┐
│  浏览器（Vue 3 SPA）                                      │
│  ┌────────────────────────────────────────────────────┐  │
│  │ 视图层  views/*  ·  组件层 components/*             │  │
│  ├────────────────────────────────────────────────────┤  │
│  │ 状态层  stores/*（auth / notice / face / review…）  │  │
│  ├────────────────────────────────────────────────────┤  │
│  │ 接口层  api/*（统一拆包、错误归一、Mock 分支）        │  │
│  ├────────────────────────────────────────────────────┤  │
│  │ 基建层  utils/request · sse · export · token        │  │
│  └────────────────────────────────────────────────────┘  │
└───────────────┬──────────────────────────────────────────┘
                │ HTTPS / WSS（Bearer Token）
┌───────────────▼──────────────────────────────────────────┐
│  Nginx：静态托管 + /api 反代 + /ws 升级                   │
└───────────────┬──────────────────────────────────────────┘
┌───────────────▼──────────────────────────────────────────┐
│  FastAPI（uvicorn）                                       │
│  routers → services → repositories → models               │
│  鉴权中间件 · 统一响应 · 审计日志 · 限流                   │
└───┬───────────────┬──────────────────┬───────────────────┘
    │               │                  │
┌───▼────┐   ┌──────▼──────┐   ┌───────▼────────┐
│ MySQL  │   │ 文件存储     │   │ 算法服务        │
│ 8.0    │   │ disk/MinIO  │   │ 本地进程或 HTTP │
└────────┘   └─────────────┘   └────────────────┘
```

### 4.2 技术选型与理由

| 层 | 选型 | 为什么是它 | 放弃了什么 |
| --- | --- | --- | --- |
| 前端框架 | Vue 3 + `<script setup>` + TS | 上手快、模板语义直观，团队里非前端专业的同学也能改 | React 生态更大，但学习曲线对本项目不划算 |
| UI | Element Plus | 表格/表单/弹窗齐全，学校场景够用 | Ant Design Vue 也行，切换成本高 |
| 状态 | Pinia（setup 写法） | 与组合式 API 一致，类型推导好 | Vuex 已过时 |
| 构建 | Vite | 冷启动秒级，HMR 快 | Webpack 配置成本高 |
| 图表 | **手写 SVG** | 只用折线/进度条，引 ECharts 多 300KB | ECharts（后续复杂图表再引） |
| 导出 | **零依赖**（CSV + 打印页） | 不引 xlsx/jspdf，包体不膨胀 | 服务端生成 xlsx（作为二期可选项） |
| 后端 | FastAPI | `types/*.ts` 与 pydantic 一一对应，`/docs` 自带联调页 | Django 太重，Flask 缺类型校验 |
| ORM | SQLAlchemy 2.0 | 类型化查询，防注入 | 原生 SQL 维护成本高 |
| 数据库 | MySQL 8.0 | 校内运维熟悉，JSON 类型够用 | PostgreSQL 更好，但院方只维护 MySQL |
| 鉴权 | JWT | 无状态、前后端分离友好 | Session 需额外存储 |

### 4.3 为什么保留 Mock 层（不是临时脚手架）

前端 16 个页面全部可在 `VITE_USE_MOCK=true` 下独立运行，这不是「偷懒」而是三条工程约束：

1. **前后端并行**。后端还没起来时，前端靠 Mock 定契约、做视觉验收，不阻塞。
2. **可演示**。答辩/汇报场地没有后端也能完整走一遍（页面顶部有「演示模式」提示，不会假装是真数据）。
3. **契约即测试**。`mock/*.ts` 与真实接口同构，字段一旦对不上，切真实接口立刻暴露。

约束：Mock 只在 `dev` 生效，**生产构建强制关闭**（`utils/env.ts`），避免把演示数据带上线。

## 5. 模块设计

### 5.1 七个评价模块的统一结构

| 层 | 约定 |
| --- | --- |
| 类型 | `types/<模块>.ts`，一个模块一套 `Record / Query / Form` |
| 接口 | `api/<模块>.ts`，每个函数一行注释写方法与路径，Mock 分支写在同一文件内 |
| 状态 | 跨页共享的才进 `stores/`（如 `review.ts` 的 `activeStudentId`） |
| 页面 | `views/modules/<模块>/index.vue`，统一套 `ModuleShell`（左操作区 + 右 340px 接口面板） |
| 契约 | 页面右侧「接口」面板即后端施工依据，README 只做索引 |

**五个环节的权重是硬约定**：签到与着装 0.15 / 食材预处理 0.20 / 烹饪过程 0.30 / 菜肴成品 0.30 /
课堂问答 0.05，合计 1.0。权重**由接口下发**（`stages[].weight`），前端不写死，便于教研组调整。

### 5.2 复核流转（本期新增的关键闭环）

```
AI 初评 ──▶ pending ──教师确认──▶ confirmed ──▶ 归档（分数冻结）
                 │
                 ├──教师驳回（必填原因 ≥4 字）──▶ rejected
                 └──教师转复核（必填原因）──────▶ reviewing
```

设计要点：

- **归档前置条件 = `confirmed`**。没有这一步，「复核」只是个装饰。
- 三态收敛为一个枚举 + 一个 `ReviewActions` 组件，综合评价与菜肴成品共用，
  两个模块不许各写一套文案。
- 已归档的记录按钮置灰，显示「已归档，不可变更」。

### 5.3 成绩溯源（三层下钻）

```
环节行（88 分）
   └─▶ 抽屉：该环节的每条来源记录（模块 / 时间 / 单条得分 / 抓拍图）
          └─▶ 弹窗：明细 + 快照大图 + 各维度 + 教师改分（填原因）
                 └─▶ 保存：重算环节分 + 追加一条「成绩修改记录」（原值仍可查）
```

**为什么改的是最原始那条记录**：如果允许直接改环节分，中间层就出现了「无来源的分数」，
一旦被问「这 88 分怎么来的」就答不上来。锚在最底层，任何一层都能往前追。

### 5.4 通知公告（本期打通的链路）

```
管理员写稿（draft）──发布──▶ published
                              ├─▶ 顶栏铃铛（未读红点 / 最近 5 条）
                              ├─▶ 工作台公告卡（置顶优先）
                              └─▶ 公告中心 /notices（全量 + 未读筛选）
```

- 三处读**同一个接口**，按 `audience`（全站 / 指定角色）过滤，服务端二次校验角色。
- 已读状态：前端按账号存本地集合（离线也能消退红点），服务端用 `notice_reads` 去重修计数。
- 撤回 = 回到草稿，接收端立即不可见。

### 5.5 语音播报（解耦后的形态）

- 配置独立走 `GET/PUT /voice/config`，**不随烹饪看板返回**——摄像头挂了、WS 断了，开关照样能改。
- 播报触发只取决于**事件到达**，与 WS 连接状态无关。
- 前端本地缓存一份配置，服务端同步失败只提示「尚未同步」，不禁用控件。
- 浏览器 TTS 需一次用户手势解锁，页面挂一次性 `pointerdown/keydown`。

## 6. 数据设计

### 6.1 核心实体

| 实体 | 主键 | 关键字段 | 说明 |
| --- | --- | --- | --- |
| `users` | id | username, role, student_no, face_key, status | 账号；`role` 决定能力点 |
| `classes` | id | name, grade, major, teacher_id | 班级 |
| `courses` | id | title, class_id, recipe_key | 课程与菜谱 |
| `tasks` | id | course_id, lesson_at, class_id | 一次实训（课前布置） |
| `face_records` | id | student_id, checked_at, similarity, status | 签到记录，含抓拍 key |
| `module_records` | id | task_id, student_id, module, score, snapshot_key, at | 五个模块的统一记录表 |
| `summary_snapshots` | id | task_id, student_id, total, stages_json, archived_at | 归档快照，冻结分数 |
| `score_changes` | id | snapshot_id/source_id, before, after, reason, operator_id | 成绩修改记录 |
| `notices` | id | title, body, audience(JSON), status, pinned | 公告 |
| `notice_reads` | (notice_id, user_id) | read_at | 已读去重 |
| `devices` / `device_logs` | id | type, station, status | 工位与摄像头，变更留痕 |

### 6.2 三条不可违背的约束

1. **归档即冻结**：`summary_snapshots` 存的是**当时**的分数与权重快照，
   之后调权重不得影响历史成绩。
2. **原值不可覆盖**：AI 分存 `ai_score`，教师分存 `final_score`，改分写 `score_changes`。
   任何一个数字都必须能回答「谁在什么时候把它从多少改成了多少」。
3. **审计只追加**：签到代签、事件确认、步骤改判、成绩改分、公告发布全部写流水，
   不允许「只改状态不留痕」。

### 6.3 数据保留与删除

| 数据 | 保留期 | 到期处理 | 依据 |
| --- | --- | --- | --- |
| 成绩与档案 | 学籍有效期 + 3 年 | 归档冷存 | 教务存档要求 |
| 人脸照片 | 学籍有效期内 | 学生离校后 30 天内软删 | 个人信息最小必要 |
| 课堂录像 | 1 个学期 | 自动清理（保留评分抓拍帧） | 存储成本 + 隐私 |
| 操作日志 | 1 年 | 归档 | 争议追溯 |

## 7. 接口规范

| 项 | 约定 |
| --- | --- |
| 风格 | REST，资源名复数，动词用子路径（`/notices/{id}/publish`） |
| 前缀 | `/api/v1/`（`VITE_API_BASE_URL` 配置） |
| 响应 | `{ code, data, message }`；`code=0` 成功，前端自动拆包 |
| 字段 | **camelCase**，DB 用 snake_case，在 pydantic 层转换 |
| 时间 | 字符串 `YYYY-MM-DD HH:mm`，不带 T、不带时区 |
| 分页 | `{ list, total, page, pageSize }` |
| 鉴权 | `Authorization: Bearer <token>` |
| 错误 | 同时给 HTTP 状态码与业务 `code`（见任务书 3.1） |
| 大文件 | `multipart/form-data`，字段名 `file`，返回 `{ fileId, url, name, size }` |
| 流式 | SSE（`text/event-stream`），`fetch + ReadableStream`，不用 `EventSource` |

## 8. 权限模型

权限的唯一事实来源是 `frontend/src/config/permissions.ts`（能力点 + 七模块访问矩阵），
后端照抄一份，**不允许在组件里各写 `if (role === 'teacher')`**。

| 能力点 | 学生 | 教师 | 管理员 |
| --- | --- | --- | --- |
| 看自己成绩 `dashboard.me` / `summary.report` | ✅ 仅本人 | ✅ | ✅ |
| 班级名单 `summary.roster` | ❌ | ✅ | ✅ |
| 复核流转 `summary.review` | ❌ | ✅ | ✅ |
| 成绩溯源改分 `summary.trace` | ❌ | ✅ | ✅ |
| 班级白名单 `class.roster` | ❌ | ✅ | ✅ |
| 上传课程 `course.manage` | ❌ | ✅ | ✅ |
| 用户管理 `user.manage` | ❌ | ❌ | ✅ |
| 公告发布 `notice.publish` | ❌ | ❌ | ✅ |
| 设备管理 `device.manage` | ❌ | ❌ | ✅ |
| AI 助手 `assistant.use` | ✅ | ✅ | ❌ |

**四条最容易被写错的边界**（前后端各拦一道）

1. 学生取 `face/records` 时，`studentId` 从 token 取，`className / keyword` 一律忽略。
2. 学生的 `summary/roster` 一律 403，不返回「只含自己一条」。
3. 管理员没有 AI 助手（`assistant.use` 不含 admin），组件按 `v-if` 不渲染。
4. `profile/overview` 的 `username` 参数只服务 Mock 切账号；真实环境一律取 token。

## 9. 非功能设计

| 维度 | 指标 | 措施 |
| --- | --- | --- |
| 性能 | 查询 P95 ≤ 300ms；首屏可交互 ≤ 2s | 路由分包、索引、列表分页、避免 N+1 |
| 并发 | 120 并发无 5xx | WS 单进程 + 连接上限；必要时 Redis pub/sub |
| 可用性 | 工作时段可用率 ≥ 99% | 健康检查真连 DB；进程守护 + 自动重启 |
| 兼容性 | Chrome / Edge 100+、Safari 15+；1366×768 起 | 不用最新语法糖；关键页 1280/1440/1920 截图复核 |
| 可维护性 | 新增一个模块不改公共代码 | 分层约定 + `ModuleShell` + 接口面板自文档 |
| 无障碍 | 关键操作可键盘完成；`aria-label` 覆盖图标按钮 | 表格行、卡片跳转支持 Enter/Space |
| 隐私合规 | 人脸最小必要、可撤回、可导出本人数据 | 软删 + 审计 + 留存期公示（见 6.3） |

### 11.1 功能验收（逐条可复现）

| # | 风险 | 概率 | 影响 | 应对 |
| --- | --- | --- | --- | --- |

### 13.2 演进路线

| 阶段 | 内容 | 前置条件 |
| --- | --- | --- |
| 二期 | 真模型替换规则版；识别准确率报告 | 试点班标注数据 ≥ 500 条 |
| 二期 | 服务端生成 xlsx / PDF；批量导出 | 教务处提出格式要求 |
| 三期 | 移动端（小程序）扫码签到与查成绩 | H5 版稳定运行一学期 |

这个系统存在的意义是把教师的判断留痕，不是把教师的判断替换掉。

## 附录 A 术语表

| 术语 | 含义 |
| --- | --- |
| 环节（stage） | 综合评价的五个组成部分：签到与着装、食材预处理、烹饪过程、菜肴成品、课堂问答 |
