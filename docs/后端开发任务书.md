## 3. 全局约定

### 3.1 统一响应

前端 `utils/request.ts` 会自动拆包，**只取 `data`**，`code != 0` 直接抛错。所以：

```json
{ "code": 0, "data": { }, "message": "ok" }
```

| code | 含义 | HTTP 状态码 |
| --- | --- | --- |
| 0 | 成功 | 200 |
| 40001 | 参数校验失败 | 422 |
| 40100 | 未登录 / token 失效 | 401 |
| 40300 | 角色无权访问 | 403 |
| 40400 | 资源不存在 | 404 |
| 40900 | 冲突（用户名重复、重复归档） | 409 |
| 50000 | 服务端异常 | 500 |

**不要**只靠 HTTP 200 + `code != 0`，也不要只靠状态码——两者都带上，前端两种都能处理。

### 3.2 字段命名：camelCase

前端 TS 类型就是契约，字段名必须是 camelCase：`studentNo`、`className`、`archivedAt`、`checkinRate`。
数据库列用 snake_case，在 pydantic 层转换：

```python
from pydantic import BaseModel, ConfigDict
from pydantic.alias_generators import to_camel

class CamelModel(BaseModel):
    model_config = ConfigDict(alias_generator=to_camel, populate_by_name=True, from_attributes=True)
```

> 七个模块页右侧的「接口面板」里有些示例写成 snake_case，那是文档笔误，
> 以 `frontend/src/types/` 为准，**统一 camelCase**。

### 3.3 时间

- 统一字符串 `YYYY-MM-DD HH:mm`（不带 T、不带时区后缀），前端直接用 `dayjs` 解析。
- DB 用 `DATETIME`，连接串加 `?charset=utf8mb4`，MySQL 时区设 `+08:00`。
- 不要返回 `2026-11-21T05:35:00.000Z`，会显示成少 8 小时。

### 3.4 分页

```json
{ "list": [], "total": 42, "page": 1, "pageSize": 20 }
```

### 3.5 鉴权

```
Authorization: Bearer <token>
```

登录成功返回：

```json
{ "code": 0, "data": { "token": "eyJ...", "user": { "id": 2, "name": "陈立群", "role": "teacher" } } }
```

`role` 只能是 `student | teacher | admin`。

### 3.6 上传限制

| 类型 | 字段 | 上限 | 说明 |
| --- | --- | --- | --- |
| 人脸照片 | `file` | 5MB | jpg/png，前端已压到 480px |
| 成品图 | `file` | 4MB | jpg |
| 菜谱 | `file` | 20MB | 仅 PDF |

超限返回 `40001`，`message` 写清楚（「图片不能超过 4MB」），前端会原样弹出来。

## 4. 权限

前端唯一事实来源是 `frontend/src/config/permissions.ts`，后端照它写死一份，别自己发挥：

| 能力 | 学生 | 教师 | 管理员 |
| --- | --- | --- | --- |
| 看自己的成绩 `GET /v1/dashboard/me`、`/v1/summary/{id}/report` | ✅ 仅本人 | ✅ | ✅ |
| 班级名单 `GET /v1/summary/roster` | ❌ | ✅ | ✅ |
| 复核流转 `POST /v1/summary/{id}/review` | ❌ | ✅ | ✅ |
| 成绩溯源改分 `PATCH /v1/summary/{id}/stages/{key}/sources/{sid}` | ❌ | ✅ | ✅ |
| 人脸记录 `GET /v1/face/records` | ✅ 仅本人 | ✅ 全员 | ✅ 全员 |
| 个人中心 `GET /v1/profile/overview`、`PUT /v1/profile/contact` | ✅ 仅本人 | ✅ 仅本人 | ✅ 仅本人 |
| 班级白名单 `GET /v1/classes`、`/v1/classes/{id}/whitelist*` | ❌ | ✅ | ✅ |
| 语音配置 `GET/PUT /v1/voice/config` | ❌ | ✅ | ✅ |
| 模块内扣分 `POST /v1/modules/.../deductions` | ❌ | ✅ | ✅ |
| 归档 `POST /v1/summary/{id}/archive` | ❌ | ✅ | ✅ |
| 上传课程 `POST /v1/courses` | ❌ | ✅ | ✅ |
| 用户管理 `/v1/users*` | ❌ | ❌ | ✅ |
| 通知发布 `/v1/notices`（写） | ❌ | ❌ | ✅ |
| 问答 `POST /v1/chat` | ✅ | ✅ | ❌ |

依赖注入写法：

```python
def require_roles(*roles: str):
    def _dep(user: User = Depends(get_current_user)) -> User:
        if user.role not in roles:
            raise ApiError(40300, "无权访问", status=403)
        return user
    return _dep

@router.get("/v1/users")
def list_users(_: User = Depends(require_roles("admin"))): ...
```

**三条最容易写错的边界**

1. 学生请求 `GET /v1/summary/{id}/report` 时，`id` 必须等于本人，否则 403（前端也拦了一道，但后端必须拦）。
2. 学生的 `GET /v1/summary/roster` 一律 403，不要"返回只含他自己的一条"——接口语义不同。
3. `POST /v1/chat` 管理员不可用（`assistant.use` 不含 admin）。
4. 学生请求 `GET /v1/face/records` 时，**忽略** `className / studentKeyword`，强制按 token 的 `studentId` 过滤。
   前端学生视角不渲染筛选条，但如果后端不强制，改个 URL 就能看全班。
5. `GET /profile/overview` 的 `username` 参数只服务 Mock 切换账号；**真实环境一律取 token**，
   传入别人的 `username` 必须忽略，否则就是一个水平越权漏洞。

## 5. 数据库

字符集统一 `utf8mb4` + `utf8mb4_0900_ai_ci`（MySQL 8），引擎 InnoDB。
下面是核心表，**可以直接执行**；字段注释里标了对应的前端类型字段。

```sql
CREATE DATABASE IF NOT EXISTS culinary
  DEFAULT CHARACTER SET utf8mb4 COLLATE utf8mb4_0900_ai_ci;
USE culinary;

-- 账号 ------------------------------------------------------------------
CREATE TABLE users (
  id            BIGINT PRIMARY KEY AUTO_INCREMENT,
  username      VARCHAR(64)  NOT NULL UNIQUE,        -- 学生用学号
  password_hash VARCHAR(128) NOT NULL,
  name          VARCHAR(32)  NOT NULL,
  role          ENUM('student','teacher','admin') NOT NULL,
  student_no    VARCHAR(32)  NULL,
  phone         VARCHAR(20)  NULL,
  email         VARCHAR(128) NULL,
  department    VARCHAR(64)  NULL,                   -- 「烹饪工艺与营养 2301」
  face_photo    VARCHAR(255) NULL,                   -- 人脸底库 URL
  face_registered TINYINT(1) NOT NULL DEFAULT 0,
  status        TINYINT      NOT NULL DEFAULT 1,      -- 1 启用 0 停用
  created_at    DATETIME     NOT NULL DEFAULT CURRENT_TIMESTAMP,
  last_login_at DATETIME     NULL,
  KEY idx_role (role), KEY idx_student_no (student_no)
) ENGINE=InnoDB;

-- 班级与花名册 ----------------------------------------------------------
CREATE TABLE classes (
  id   BIGINT PRIMARY KEY AUTO_INCREMENT,
  name VARCHAR(64) NOT NULL UNIQUE                    -- 「烹饪工艺与营养 2301」
) ENGINE=InnoDB;

CREATE TABLE class_students (
  class_id   BIGINT NOT NULL,
  user_id    BIGINT NOT NULL,
  seat       VARCHAR(8) NOT NULL,                     -- 工位号，前端 SummaryStudent.seat
  PRIMARY KEY (class_id, user_id)
) ENGINE=InnoDB;

-- 课程与菜谱 ------------------------------------------------------------
CREATE TABLE courses (
  id          BIGINT PRIMARY KEY AUTO_INCREMENT,
  title       VARCHAR(128) NOT NULL,
  class_id    BIGINT NOT NULL,
  teacher_id  BIGINT NOT NULL,
  goal        VARCHAR(255) NULL,
  dishes      JSON NULL,                              -- ["糖醋里脊","上汤娃娃菜"]
  lesson_at   DATETIME NOT NULL,
  recipe_url  VARCHAR(255) NULL,                      -- 菜谱 PDF
  published   TINYINT(1) NOT NULL DEFAULT 0,
  created_at  DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP
) ENGINE=InnoDB;

-- 实训任务（一节课 = 一个 task，所有评价记录挂在它下面）----------------
CREATE TABLE tasks (
  id          VARCHAR(32) PRIMARY KEY,                -- "task_20261121_01"
  course_id   BIGINT NOT NULL,
  class_id    BIGINT NOT NULL,
  teacher_id  BIGINT NOT NULL,
  lesson_at   DATETIME NOT NULL,
  status      ENUM('running','finished','archived') NOT NULL DEFAULT 'running'
) ENGINE=InnoDB;

-- 签到 ------------------------------------------------------------------
CREATE TABLE checkins (
  id          BIGINT PRIMARY KEY AUTO_INCREMENT,
  task_id     VARCHAR(32) NOT NULL,
  student_id  BIGINT NOT NULL,
  similarity  DECIMAL(5,4) NOT NULL,                  -- 0.9640
  image_url   VARCHAR(255) NULL,
  checked_at  DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
  UNIQUE KEY uk_task_student (task_id, student_id)
) ENGINE=InnoDB;

-- 各模块判定结果（一个模块一个 JSON，够用且好扩展）--------------------
CREATE TABLE module_results (
  id          BIGINT PRIMARY KEY AUTO_INCREMENT,
  task_id     VARCHAR(32) NOT NULL,
  student_id  BIGINT NOT NULL,
  module      VARCHAR(24) NOT NULL,                   -- uniform/ingredient/cooking/dish
  score       DECIMAL(5,1) NOT NULL,
  detail      JSON NOT NULL,                          -- 该模块的判定明细
  created_at  DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
  UNIQUE KEY uk_task_student_module (task_id, student_id, module)
) ENGINE=InnoDB;

-- 教师现场扣分（与学生成绩分开存，谁扣的、为什么扣都要留痕）------------
CREATE TABLE deductions (
  id          BIGINT PRIMARY KEY AUTO_INCREMENT,
  task_id     VARCHAR(32) NOT NULL,
  student_id  BIGINT NOT NULL,
  module      VARCHAR(24) NOT NULL,
  item        VARCHAR(64) NOT NULL,                   -- 违规项，如「未戴厨师帽」
  points      INT NOT NULL,
  reason      VARCHAR(255) NOT NULL,
  created_by  BIGINT NOT NULL,                        -- teacher id
  created_at  DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
  KEY idx_task_student (task_id, student_id)
) ENGINE=InnoDB;

-- 综合评价与归档快照 ----------------------------------------------------
CREATE TABLE summaries (
  id          BIGINT PRIMARY KEY AUTO_INCREMENT,
  task_id     VARCHAR(32) NOT NULL,
  student_id  BIGINT NOT NULL,
  weighted    DECIMAL(5,1) NOT NULL,                  -- 加权分（未扣教师分）
  deducted    INT NOT NULL DEFAULT 0,
  total       INT NOT NULL,                           -- 最终分
  grade       VARCHAR(8) NOT NULL,                    -- 优秀/良好/中等/及格/不及格
  stages      JSON NOT NULL,                          -- [{key,label,weight,score,records}]
  confirmed   TINYINT(1) NOT NULL DEFAULT 0,
  archived_at DATETIME NULL,
  UNIQUE KEY uk_task_student (task_id, student_id)
) ENGINE=InnoDB;

CREATE TABLE summary_snapshots (
  id          BIGINT PRIMARY KEY AUTO_INCREMENT,
  summary_id  BIGINT NOT NULL,
  payload     JSON NOT NULL,                          -- 归档当时的完整成绩，之后权重调整不影响
  created_at  DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP
) ENGINE=InnoDB;

-- 通知与问答 ------------------------------------------------------------
CREATE TABLE notices (
  id         BIGINT PRIMARY KEY AUTO_INCREMENT,
  title      VARCHAR(128) NOT NULL,
  body       TEXT NOT NULL,
  level      ENUM('info','warning','success') NOT NULL DEFAULT 'info',
  status     ENUM('draft','published','revoked') NOT NULL DEFAULT 'draft',
  created_by BIGINT NOT NULL,
  created_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
  published_at DATETIME NULL
) ENGINE=InnoDB;

CREATE TABLE chat_sessions (
  id         BIGINT PRIMARY KEY AUTO_INCREMENT,
  user_id    BIGINT NOT NULL,
  title      VARCHAR(64) NOT NULL,
  created_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP
) ENGINE=InnoDB;

CREATE TABLE chat_messages (
  id         BIGINT PRIMARY KEY AUTO_INCREMENT,
  session_id BIGINT NOT NULL,
  role       ENUM('user','assistant') NOT NULL,
  content    MEDIUMTEXT NOT NULL,
  file_url   VARCHAR(255) NULL,
  created_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
  KEY idx_session (session_id)
) ENGINE=InnoDB;

-- 官网留资 --------------------------------------------------------------
CREATE TABLE demo_requests (
  id          BIGINT PRIMARY KEY AUTO_INCREMENT,
  request_no  VARCHAR(32) NOT NULL UNIQUE,            -- DEMO-20261121-9697
  org         VARCHAR(128) NOT NULL,
  name        VARCHAR(32)  NOT NULL,
  role        VARCHAR(32)  NOT NULL,
  phone       VARCHAR(20)  NOT NULL,
  scale       VARCHAR(32)  NOT NULL,
  plan        VARCHAR(32)  NULL,
  want        VARCHAR(32)  NULL,
  note        VARCHAR(500) NULL,
  created_at  DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
  KEY idx_phone_time (phone, created_at)
) ENGINE=InnoDB;
```

## 6. 接口清单

**前缀约定（本轮已统一）**：前端 `VITE_API_BASE_URL=/api/v1`，所以 `src/api/*.ts` 里写的是
`/face/checkin`、`/dashboard/overview` 这种**不含前缀**的路径。
本文早期章节写的 `/v1/xxx` 与它是同一个地址（`/api/v1/xxx`），新增章节一律省略前缀。
你的 FastAPI router 前缀保持 `/api/v1` 即可，两边不用改。

**"状态"列的 Mock 指的是前端本地假数据，不是你的进度。**

### 6.1 账号与鉴权

| 方法 | 路径 | 入参 | 返回 | 权限 |
| --- | --- | --- | --- | --- |
| POST | `/v1/auth/login` | `{username,password}` | `{token,user}` | 公开 |
| GET | `/v1/auth/profile` | — | `User` | 登录 |
| POST | `/v1/auth/logout` | — | `null` | 登录 |
| POST | `/v1/auth/register` | `{username,password,name,role,phone,facePhoto?}` | `{id,username,needApproval}` | 公开 |
| GET | `/v1/users` | `page,pageSize,keyword,role,status` | `PageResult<User>` | admin |
| POST | `/v1/users` | `UserForm` | `User` | admin |
| PUT | `/v1/users/{id}` | `UserForm` | `User` | admin |
| DELETE | `/v1/users/{id}` | — | `null` | admin |
| PUT | `/v1/users/{id}/face` | `{facePhoto}` (dataURL) | `null` | admin |

注册注意：`student` 角色 `needApproval=true`，账号 `status=0` 等管理员审核；`teacher` 同理。
**注册必须校验用户名唯一**，前端只会把后端的错误信息弹出来（`40900` + `该账号已存在，请更换用户名`）。

### 6.2 工作台

| 方法 | 路径 | 返回 | 权限 |
| --- | --- | --- | --- |
| GET | `/dashboard/overview?courseId&classId&taskId` | `DashboardOverview` | teacher, admin |
| GET | `/dashboard/me` | `MyOverview` | student |

三个查询参数都可省，省了就是「不限」。`course/class/task` 同时给时按交集算。

`DashboardOverview` 在原有 `stats / activities / modules / checkinRate` 之外，本轮新增三块
（结构见 `types/dashboard.ts`，前端按这个渲染，字段少一个页面就少一块）：

```json
{
  "session": {
    "taskId": "task_20261121_01", "taskTitle": "糖醋里脊 · 过程实训",
    "courseId": "1", "courseTitle": "第 7 周 · 刀工与火候综合训练",
    "classId": "12", "className": "烹饪工艺与营养 2301", "teacher": "陈立群",
    "startedAt": "2026-11-21T08:00:00", "endedAt": "2026-11-21T11:40:00",
    "status": "running",
    "total": 4, "checkedIn": 4, "inTraining": 2, "completed": 2, "archived": 2,
    "cameraOnline": 4, "cameraOffline": 3,
    "pendingReview": 2, "anomalies": 4
  },
  "completion": [
    { "key": "checkin", "name": "签到与着装", "active": true, "done": 4, "total": 4 }
  ],
  "filters": {
    "courses": [{ "label": "第 7 周 · 刀工与火候综合训练", "value": "1" }],
    "classes": [{ "label": "烹饪工艺与营养 2301", "value": "12" }],
    "tasks":   [{ "label": "糖醋里脊 · 过程实训", "value": "task_20261121_01" }]
  }
}
```

**口径必须写死，否则页面上的数会对不上花名册**：

| 字段 | 定义 |
| --- | --- |
| `total` | 本次实训**应到**人数 = 该班在评学生数，不是全校在训人数 |
| `checkedIn` | 已签到人数（含教师补录） |
| `inTraining` | 已签到、成品未提交：`checkedIn - completed`，不要为负 |
| `completed` | 五个环节全部结束的人数（归档是另一件事） |
| `archived` | 已归档份数，归档后分数冻结 |
| `pendingReview` | 待复核 = 应到 - 已归档 |
| `anomalies` | **未确认**的异常事件数；已确认的留在档案里不重复计 |
| `cameraOnline/Offline` | 与本次实训工位绑定的摄像头，按 `status='online'` 计 |
| `completion[].active` | 该模块本节是否开启；`false` 时前端不显示完成率（分母为 0 会显示成 0%，是错的） |

筛不到任何任务时 `session` 返回 `null`，**不要**返回一个全 0 的对象——前端会用一句话说明
「这个筛选条件下没有实训任务」，而 8 个 0 会被读成「这个班一个人都没来」。

`MyOverview` 只能含本人数据（`stats / stages / todos / activities`），**不要**把班级签到率塞进去。
本轮新增三个字段：

```json
{
  "seat": "02",
  "task": { "id": "task_20261121_01", "title": "糖醋里脊 · 过程实训", "status": "running",
            "startedAt": "2026-11-21T08:00:00", "endedAt": "2026-11-21T11:40:00", "step": "翻炒" },
  "checkin": { "status": "checked_in", "at": "2026-11-21 08:12", "similarity": 96.4, "deviceName": "CAM-A-001" },
  "archived": [
    { "id": "arch_1001_prev", "taskTitle": "刀工与火候 · 补练", "archivedAt": "2026-11-20 14:02",
      "total": 88, "grade": "良好", "ruleVersion": "2026.11-v1.2" }
  ]
}
```

`checkin.status`：`checked_in`（本人人脸）/ `manual`（教师补录，必须带 `operator`）/ `missing`。
`archived` 只放**已归档**的历史，进行中的本节成绩仍走 `stages`，两者混在一起学生会误读。
学生只能拿到自己的 `stages / archived`，越权返回 `403`。

#### 6.5.1 人脸签到

```http
POST /face/checkin            Body: { "image": "<base64 jpeg>", "deviceId": "CAM-A-001" }
GET  /face/records?page=1&pageSize=10&studentId=1001&studentKeyword&className&status&startDate&endDate
GET  /face/records/{id}
POST /face/checkin/manual     Body: { "studentId": 1001, "checkedAt": "2026-11-21T08:20:00", "reason": "…" }
GET  /face/profiles
POST /face/profiles/{userId}  Body: { "image": "<base64 jpeg>" }
DELETE /face/profiles/{userId} Body: { "reason": "…" }
```

- `checkin` 必须支持**多人同框**：返回 `matches: [{userId,name,studentNo,status}]`，
  `status` 取 `success / unregistered / duplicate`；单人也按数组返回，前端不再分支。
- 相似度阈值、重签（同一人重复签到）由后端判 `duplicate`，前端只负责提示。
- 底库注销是**软删**并写审计（谁、什么时候、为什么），撤销后该生签到返回 `unregistered`。
- `records` 支持分页与筛选，返回 `PageResult<FaceRecord>`；`status` 取 `success/failed/duplicate/manual`。
- **学生只能看自己的记录**：学生 token 调 `records` 时，后端必须**忽略** `className / studentKeyword`，
  强制按 token 里的 `studentId` 过滤；教师 / 管理员才允许按班级、学号关键字查全员。
  前端的筛选条在学生视角直接不渲染，但那只挡 UI，不挡请求——真正的隔离必须在服务端。
- 补录必须写 `operatorId`，前端详情里会显示「由谁补录」，这是查代签的唯一凭据。

#### 6.5.2 烹饪过程

```http
GET  /modules/cooking/board?studentId=1001
POST /modules/cooking/events/{id}/ack       Body: { "note": "…" }
POST /modules/cooking/steps/{key}/review    Body: { "status": "done|abnormal|review", "note": "…" }
PUT  /modules/cooking/channels/{id}         Body: { "name": "…", "station": "02" }
```

- **视频流与事件流分开**：媒体走 `ws://…/ws/media/{channelId}`（或 HLS/WebRTC），
  `WS /ws/cooking` 只推 `{type:"event"|"step"|"heartbeat", data}`。断流时前端不显示任何伪造事件。
- `board` 返回 `{channels, steps, events}`，通道集合四种状态：
  `online / connecting / offline / failed`，前端按状态渲染占位（连接中转圈、失败给重连按钮）。
- **`board` 不再返回 `voice`**：语音配置已拆成独立接口（6.10.3）。这样摄像头挂掉、WS 连不上时，
  播报开关照样能读能改——原来的 `PUT /modules/cooking/voice` 已废弃，别再实现。
- `review`、`ack` 都要落审计（人、时间、说明），前端详情里直接展示，不允许只改状态不留痕。
- 播报文本由后端在事件里给 `ttsText`，前端只用浏览器 TTS，不自造文案。

#### 6.5.3 菜肴成品

```http
POST /dish/analyze        Body: { "fileId": "f_xxx", "studentId": 1001 }
POST /dish/{id}/override  Body: { "dimensions": [{ "key": "plating", "score": 88 }], "reason": "…" }
POST /dish/{id}/review    Body: { "action": "confirm|reject|hold", "note": "按 20 分制重新核定…" }
GET  /dish/history?studentId=1001
```

- 五维必须带 `score / weight / reason / advice`；`total` 由后端按权重算，权重和必须为 1。
- `override` 只改教师那一层，**原始 AI 分存在 `aiScore` 里不许覆盖**，前端会同时显示两个数。
- `review` 是教师复核的三态流转（确认 / 驳回 / 转复核），返回 `{ reviewState, reviewedBy, reviewedAt }`；
  `reject` 与 `hold` **必须带 `note`**（前端已强制 ≥4 字），后端仍要校验，空原因返回 `40001`。
- `analyze` 返回里必须有 `disclaimer`：照片不能判断真实口味、内部熟度与食品安全。

**五个环节与权重是硬约定**：`0.15 / 0.20 / 0.30 / 0.30 / 0.05`，合计 1.0。

**复核三态**：`reviewState` 取 `pending / confirmed / rejected / reviewing`，缺省按 `pending` 处理。

```http
POST  /v1/summary/{studentId}/review
Body: { "taskId": "task_20261121_01", "action": "confirm|reject|hold", "note": "…" }
```

- `confirm` → `confirmed`，此后才允许归档；`reject` → `rejected`；`hold` → `reviewing`（转复核）。
- `reject` / `hold` **必须带 note（≥4 字）**，写进 `summary_reviews` 表，前端在名单里直接显示原因。
- 已归档的成绩不允许再改复核状态，返回 `40900`（「已归档，不可变更」）。

**成绩溯源与改分**

```http
GET   /v1/summary/{studentId}/stages/{stageKey}/sources?taskId=...
PATCH /v1/summary/{studentId}/stages/{stageKey}/sources/{sourceId}
Body: { "score": 92, "reason": "画面遮挡误判，现场确认已烧干" }
```

- `sources` 返回 `ScoreSource[]`：`{ id, module, label, at, score, snapshot, dimensions?, meta? }`，
  `snapshot` 是抓拍图 URL（签到时的人脸图、成品的成品照、烹饪的事件帧），**没图就给 null，别给占位图**。
- `PATCH` 改的是**最原始那条记录的分**，不是环节分：返回后由后端按剩余来源重新算 `stages[].score`，
  并把这次改动写成一条 `ScoreChange { id, field, before, after, reason, operator, at }` 追加到
  `students[].changes`——前端「成绩修改记录」表就渲染这个数组。
- 改分必须留 `reason` 与 `operator`，且**原值不许被覆盖**（`before` 落库）。追溯链断在这里就没法查账了。

```http
GET /v1/summary/{studentId}/report?taskId=...
```

学生本人、教师、管理员。返回 `SummaryReportData`：

```json
{
  "code": 0,
  "data": {
    "student": { "...": "同 roster 里的单项" },
    "total": 91,
    "grade": "优秀",
    "task": { "id": "task_20261121_01", "courseTitle": "…" },
    "generatedAt": "2026-11-21 13:40"
  }
}
```

`total` 是**加权分（未扣教师现场分）**，教师扣分由前端从复核记录里合成后扣减。
如果你想让后端算好最终分，加一个 `finalScore` 字段即可，前端会优先用它——但要同时返回 `deducted`。

```http
POST /v1/summary/{studentId}/archive
Body: { "taskId": "task_20261121_01" }
```

教师 / 管理员。锁定分数、写 `summary_snapshots`，返回 `{ archivedAt, snapshotId }`。
已归档再调用返回 `40900`（「该成绩已归档」），前端会提示。

**归档规则**

1. `total < 60` 时可以先要求复核：后端返回 `40900` + `低于 60 分需复核后再归档`，前端会照弹。
2. 归档后权重表调整**不得**影响历史成绩——快照就是为了这个。
3. 归档是幂等的边界：教师重复点不该产生两份快照。

  不要为了「字段齐全」给教师塞一份空成绩，那会让前端误判。
- `scores.latest` 必须与 `GET /v1/summary/.../report` 的 `total` **同源同值**，两边不一致会被学生当场发现。
- `PUT /profile/contact` 只允许改**自己的**手机与邮箱；学号、班级、姓名由教务同步，收到这些字段直接忽略。

#### 6.10.2 班级白名单

位置说明：入口在**教学 → 班级名单**，不在「系统管理」。系统管理是管理员的账号维护，
而「把这学期名单导进来」是任课教师开课第一天的活，教师进不去系统管理。

```http
GET  /classes                                  → ClassBrief[]
POST /classes/{id}/whitelist/parse
Body: { "text": "2023010111\t王小明\t13800000011\n2023010112,李小红" }
     → { "rows": WhitelistRow[], "summary": { "total": 3, "creatable": 1, "exists": 1, "invalid": 1 } }
POST /classes/{id}/whitelist
Body: { "rows": [{ "line": 2, "studentNo": "2023010111", "name": "王小明", "phone": "13800000011" }] }
     → { "batchId": "WL-20261122-001", "created": 1, "skipped": 2 }
```

**为什么拆成 parse + import 两步**：教师在**提交前**必须看到哪几行有问题（学号位数不对、重复、库里已有），
一步到位的接口只能事后报错，名单里混进一条脏数据就得多导一次。

- 解析规则：按 `\t , ， ; ；` 切列，没有这些分隔符时按空格切；**空列要保留**——
  `2023010154\t\t138…` 缺姓名，若把连续分隔符合并，手机会被当成姓名存进去。
- 校验：学号 `^\d{8,14}$`；姓名不能为空、不能以数字开头（列错位的信号）；手机号可空，非空则 `^1\d{10}$`。
- 判重：**库里已有学号 → `exists`，跳过且不覆盖**（教师改过的资料不能被一次导入冲掉）；同一份文本里重复 → `invalid`。
- `import` 只为 `creatable` 的行建账号，其余原样返回计数；**整批失败要能整体回滚**，不要建一半。
- 新建的学生默认没有密码人脸，状态为「待开通」，首次登录走注册流程采集人脸。

#### 6.10.3 语音配置

```http
GET /voice/config?station=A-02   → VoiceConfig
PUT /voice/config  Body: { "enabled": true, "volume": 70, "strategy": "critical|all|none",
                           "announceStation": true, "station": "A-02", "rate": 1 }
```

```json
{ "enabled": true, "volume": 70, "strategy": "critical", "announceStation": true,
  "station": "A-02", "rate": 1, "updatedAt": "2026-11-22T09:12:00" }
```

- **必须与 WebSocket、媒体流完全解耦**。这是修 bug 修出来的约定：原来的语音开关跟 `board` 一起返回，
  摄像头一挂整块读不到，教师看到开关是灰的以为没这功能。
- 前端在 `localStorage` 存了一份（`culinary_ai_voice_config`），断网也能开关；读服务端失败只提示
  「尚未同步到服务器」，**不把开关禁用**。
- 播报触发只取决于**事件到达**，与 `WS /ws/cooking` 的 `connected` 状态无关；`enabled=false` 时静默且不排队。
- 策略按**工位**生效，`announceStation=true` 时播报文本前拼工位号，避免一间教室四个工位同时播报串线。
- TTS 在浏览器本地跑（`speechSynthesis`），后端不需要存音频；`rate` 只调语速，别在服务端做语音合成。

### 6.11 通知公告

一条公告从「管理员写」到「学生看到」经过三处页面：顶栏铃铛、工作台公告卡、公告中心（`/notices`）。
三处读的是同一个接口，**不要为某个位置单独开接口**——之前前端就是因为铃铛接了一份写死的假数据，
导致「发布了但哪里都没出现」。

```http
GET    /notices                     接收端：只返回已发布 + 按 token 角色过滤
GET    /notices?scope=manage        管理端：含草稿，仅 admin
POST   /notices                     新建（落库即为 draft）
PUT    /notices/{id}                编辑（已发布的也可以改，改完立即对接收端生效）
POST   /notices/{id}/publish        发布：status=published，写 publishedAt
POST   /notices/{id}/revoke         撤回：回到 draft，publishedAt 置空
DELETE /notices/{id}                删除
POST   /notices/{id}/read           标记本人已读，返回最新 readCount
```

`Notice` 结构（`types/notice.ts`）：

```json
{
  "id": 1004,
  "title": "关于期末实训评价口径调整",
  "body": "期末综合评价的权重方案拟调整为……\n\n待教研组会讨论后发布。",
  "type": "system",
  "status": "published",
  "pinned": false,
  "audience": ["teacher"],
  "publisher": "张明远",
  "createdAt": "2026-11-20 11:48",
  "publishedAt": "2026-11-22 17:19",
  "readCount": 0,
  "totalCount": 61
}
```

**四条必须守住的规则**

1. **接收端必须过两道过滤**：`status = 'published'` **且**（`audience = 'all'` 或 token 的 role 在
   `audience` 里）。只按前端传来的 role 过滤是不行的——学生改个 query 就能读到教师公告。
2. `GET /notices`（接收端）**不返回草稿**，也不要「顺手返回草稿但前端不显示」：数据一旦下发，
   就等于泄露了未定稿的教研决策。
3. `totalCount` 由服务端按「当前在册且角色匹配的账号数」实时算，**不接受前端传**。
   已读人数靠 `notice_reads` 的去重行数算，不靠自增计数器（重复点击会虚高）。
4. `readCount / totalCount` 只是聚合数；**谁读过**要落 `notice_reads`，那是「通知是否送达」的
   唯一凭据，也是争议时能自证的材料。

```sql
CREATE TABLE `notices` (
  `id`           BIGINT UNSIGNED NOT NULL AUTO_INCREMENT,
  `title`        VARCHAR(120)    NOT NULL,
  `body`         TEXT            NOT NULL,
  `type`         ENUM('system','feature','maintenance') NOT NULL DEFAULT 'system',
  `status`       ENUM('draft','published') NOT NULL DEFAULT 'draft',
  `pinned`       TINYINT(1)      NOT NULL DEFAULT 0,
  -- 'all' 或 JSON 数组 '["teacher","admin"]'；用 JSON 而不是逗号串，便于按角色过滤
  `audience`     JSON            NOT NULL,
  `publisher_id` BIGINT UNSIGNED NOT NULL,
  `created_at`   DATETIME        NOT NULL DEFAULT CURRENT_TIMESTAMP,
  `published_at` DATETIME        NULL,
  PRIMARY KEY (`id`),
  KEY `idx_status_pub` (`status`, `published_at`),
  KEY `idx_pinned` (`pinned`)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='通知公告';

CREATE TABLE `notice_reads` (
  `notice_id` BIGINT UNSIGNED NOT NULL,
  `user_id`   BIGINT UNSIGNED NOT NULL,
  `read_at`   DATETIME        NOT NULL DEFAULT CURRENT_TIMESTAMP,
  PRIMARY KEY (`notice_id`, `user_id`),   -- 复合主键天然去重，重复标记不会多算
  KEY `idx_user` (`user_id`)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='公告已读记录';
```

`audience` 的过滤写法（MySQL 8，JSON 数组用 `JSON_CONTAINS`）：

```python
# SQLAlchemy 2.0
stmt = select(Notice).where(Notice.status == "published")
if user.role != "admin":                       # 管理员看全量（含草稿走另一分支）
    stmt = stmt.where(
        or_(Notice.audience == cast("all", JSON),
            func.json_contains(Notice.audience, json.dumps(user.role)) == 1)
    )
```

**已读标记的语义**：`POST /notices/{id}/read` 是**幂等**的（`INSERT IGNORE` 到 `notice_reads`），
重复调用返回同一个 `readCount`。前端在打开阅读器时就会调它，用户多点几次不能把阅读率刷上去。

## 7. 导出：成绩单与报告

前端已经实现了两个导出，**不依赖后端**：

| 导出 | 形式 | 前端实现位置 |
| --- | --- | --- |
| 成绩单（班级 / 全站 / 我的） | CSV，Excel/WPS 双击打开 | `utils/export.ts` → `downloadCsv()` |
| 单人报告 | A4 打印页，浏览器「另存为 PDF」 | `views/modules/summary/report.vue` |

**方案 A（默认，推荐）：后端不用写导出。** 数据由 6.6 的接口提供，前端即时生成，天然与屏幕一致。

**方案 B：后端发 xlsx。** 想统一服务端生成、或要带公章图片时用这个：

```python
# GET /v1/summary/export?taskId=&classId=  权限：teacher/admin；学生另开 /v1/summary/me/export
@router.get("/v1/summary/export")
def export_scores(taskId: str, classId: int | None = None, user=Depends(require_roles("teacher","admin"))):
    wb = build_workbook(taskId, classId)          # openpyxl
    buf = BytesIO(); wb.save(buf); buf.seek(0)
    filename = quote(f"综合评价-{class_label}-{date}.xlsx")
    return StreamingResponse(
        buf,
        media_type="application/vnd.openxmlformats-officedocument.spreadsheetml.sheet",
        headers={"Content-Disposition": f"attachment; filename*=UTF-8''{filename}"},
    )
```

前端切换到方案 B 只需要把 `downloadCsv(...)` 换成「请求 blob → `downloadBlob()`」，一处改动。

**方案 C：后端发 PDF。** 只有「必须服务端存档」时才做。中文字体是坑：WeasyPrint 需要显式注册
`Noto Sans CJK`，reportlab 需要 `TTFont` 指定 `.ttf`，否则中文全变方块。为了一个报告引 100MB 字体不划算。

**导出必须守的三条**

1. 学生只能导自己（`studentId` 从 token 取，不接受前端传）。
2. 学号是文本，别让 Excel 转成数字（openpyxl 设 `cell.number_format = '@'`）。
3. 文件名带范围与日期：`综合评价-烹饪工艺与营养2301-20261121.csv`。

## 8. 流式问答（SSE）的四条硬要求

前端 `utils/sse.ts` 用的是 `fetch + ReadableStream`，不是 `EventSource`（要带 Authorization 与 POST body）。

1. **响应头**：`Content-Type: text/event-stream`、`Cache-Control: no-cache`、`X-Accel-Buffering: no`。
2. **不要缓冲**：Nginx 要关 `proxy_buffering`；FastAPI 用 `StreamingResponse`，别先拼完整字符串。
3. **数据格式**：每帧 `data: {"delta":"…"}\n\n`，结束发 `data: [DONE]\n\n`。前端按 `delta` 追加。
4. **超时与中断**：客户端断开要能感知（`await request.is_disconnected()`），及时释放模型调用。

附件问答：前端先 `POST /v1/files` 拿 `file_id`，再随 `/v1/chat` 的 `fileIds` 发送（camelCase）。
后端要把文件内容转成文本/图片喂给模型，**不要把 file_id 直接丢给模型**。

## 11. 常见坑（都是踩过的）

| 现象 | 原因 | 处理 |
| --- | --- | --- |
| 前端所有请求 404 | 路由前缀漏了 `/api` | `app.include_router(r, prefix="/api")` |
| 浏览器报 CORS | 只开了 `allow_origins=["*"]` 但 `allow_credentials=True` | 显式列 5173 |

| CSV 打开乱码 | 没写 BOM | 文件头 `\ufeff` |

| 学生能看到全班成绩 | 只在前端 `v-if` 挡了 | 后端必须再判一次 |
| SSE 一次性吐出全部 | 中间层缓冲 | 见第 8 节 |

```
                          └─ /ws/         → uvicorn（WebSocket 需 Upgrade 头）
                              ├── MySQL 8.0（本机 3306，只监听 127.0.0.1）
                              └── /data/files（上传目录，独立分区）
```

```nginx
server {
    listen 443 ssl http2;
    server_name culinary.example.edu.cn;

    root /opt/culinary/dist;
    index index.html;

    # history 路由：刷新 /modules/summary 不能 404
    location / {
        try_files $uri $uri/ /index.html;
    }

    location /api/ {
        proxy_pass http://127.0.0.1:8000;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        client_max_body_size 25m;          # 与后端上传上限对齐，否则 413 在前端表现为「上传失败」
    }

    location /ws/ {
        proxy_pass http://127.0.0.1:8000;
        proxy_http_version 1.1;
        proxy_set_header Upgrade $http_upgrade;
        proxy_set_header Connection "upgrade";
        proxy_read_timeout 300s;           # WS 空闲会被默认 60s 掐断
    }
}
```

**环境变量（`.env.example` 至少这些）**

```ini
APP_ENV=production
SECRET_KEY=<openssl rand -hex 32 生成，不要用默认值>
DATABASE_URL=mysql+pymysql://culinary:***@127.0.0.1:3306/culinary?charset=utf8mb4
UPLOAD_DIR=/data/files
MAX_UPLOAD_MB=20
TOKEN_EXPIRE_MINUTES=720
CORS_ORIGINS=https://culinary.example.edu.cn
```

**进程管理**：`uvicorn` 用 `--workers 4`（不要开 `--reload`），配 systemd 或 supervisor 自启；
WS 场景若上多进程，事件广播要走 Redis pub/sub，否则 A 进程推的事件 B 进程的客户端收不到。

**发布顺序**：先跑 `sql/migrations/` 里的增量脚本 → 再发后端 → 最后刷前端静态文件。
前端先发会调到不存在的接口，用户看到的是白屏，比"功能没上"更糟。

## 16. 日志与监控

**结构化日志（JSON 一行一条）**，字段固定：

| 字段 | 例子 | 用途 |
| --- | --- | --- |
| `ts` | `2026-11-22T17:19:03+08:00` | 排序、对齐前端时间 |
| `level` | `INFO / WARN / ERROR` | 告警分级 |
| `trace_id` | `8f2c…` | 一次请求贯穿前后端，前端报错时让用户截图这个 |
| `method` / `path` | `POST /api/v1/summary/1001/review` | 定位 |
| `user_id` / `role` | `2 / teacher` | 谁触发的 |
| `status` / `cost_ms` | `200 / 143` | 慢查询排查 |
| `msg` | `archive blocked: review not confirmed` | 人看的那句话 |

**必须埋的四个指标**（Prometheus 或每天一次 SQL 统计都行）：

1. 各接口 `P95 耗时` 与 `5xx 计数`；
2. 登录失败次数（按账号聚合，防撞库）；
3. 人脸识别成功/未注册/重复签到三条计数（阈值突然偏移说明模型或阈值动了）；
4. 未读公告数、待复核数（业务侧「有没有积压」）。

**告警阈值建议**：5xx > 1%/5min；识别接口 P95 > 5s 持续 10 分钟；磁盘 > 85%；数据库连接池耗尽。

**健康检查**：`GET /health` 返回 `{status, db, version}`，db 要真的 `SELECT 1`，
不要只 return OK——那种健康检查在数据库挂了的时候仍然报健康，比没有更误导。

## 17. 测试策略与验收 DoD

**三层，够用就行，不要为了覆盖率写空测试**

| 层 | 范围 | 工具 | 通过标准 |
| --- | --- | --- | --- |
| 冒烟 | 每个接口一条正常路径 | `tests/smoke.py`（httpx） | 全绿，一条命令跑完 |
| 契约 | 关键接口字段与 `types/*.ts` 一致 | pydantic 模型 + 断言 | 字段名、类型、可空性都对 |
| 越权 | 学生访问教师接口 / 访问他人资源 | 参数化用例 | 全部 403，无一例外 |

**必须写的 8 条越权用例**（这是评审最容易挑的地方）

1. 学生 `GET /face/records?className=...` → 只返回自己的；
2. 学生 `GET /summary/{别人id}/report` → 403；
3. 学生 `POST /summary/{id}/review` → 403；
4. 学生 `GET /summary/roster` → 403；
5. 学生 `GET /notices` 不能拿到 `audience=['teacher']` 的公告；
6. 教师 `GET /users` → 403；
7. 教师 `DELETE /notices/{id}` → 403（只有 admin）；
8. 无 token 访问任意业务接口 → 401（不是 500）。

**验收 DoD（Definition of Done）**

- [ ] `VITE_USE_MOCK=false` 后，三种角色各自把 16 个页面点一遍，控制台零红色报错；
- [ ] 公告：管理员发布后，教师在铃铛/工作台/公告中心三处都能看到，学生看不到教师专属公告；
- [ ] 复核：未 `confirm` 的学生点归档被拒；驳回必须带原因；
- [ ] 成绩溯源：改一条来源记录的分数，下方「成绩修改记录」立即多一行，原值仍可查；
- [ ] 导出：CSV 用 Excel 双击能正常显示中文，学号不变成科学计数法；
- [ ] 白名单：一份含脏数据的名单导入后，脏行有明确原因、干净行全部入册；
- [ ] `sql/schema.sql` 在空库执行一遍能起来（不是靠手工补表）；
- [ ] 部署说明换一台机器能照做成功。
